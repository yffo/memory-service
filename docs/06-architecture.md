## 1. 一句话定位与边界

**tabellio 是一个跨宿主的本地长期记忆服务**（目标形态）：一份纯文本事实库 + 一个 MCP 服务 + 一个空闲期巩固进程（后台自动巩固尚未实现；显式 `consolidate` 已可用）；任何 CLI / IDE / 自研 agent 通过 MCP 工具按需读写它，拿到的是带来源、带有效期、带信任等级的记忆内容。

三个词各自落到实处。**跨宿主**：唯一一等接口是 MCP，DSH 插件与 CLI 都只是壳；靠「读同一批文件 + 同一套工具语义」保持一致，不靠同步。**服务而不是插件**：插件可以只服务一个宿主、可以深挖那个宿主的私有能力；服务要在 11 个宿主里至少 3 个上跑通同一套语义（宿主清单见 `03-hosts-and-interfaces.md`）。**本地长期**：默认零 API 成本、纯文本落盘、`cat` 得出、git 管得住、随时带走。

**不做的事（写清楚，避免以后扯皮）**：

| 不做 | 为什么 | 何时重议 |
|---|---|---|
| 云 SaaS、托管服务 | 不做多用户/团队共享（`00-brief.md §4`）；也不碰别人的数据 | 不做。这是定位不是阶段 |
| 模型训练 / 微调 | 训练侧记忆到今天没有一项能力是「花钱就能买到」（`05-agi-direction.md §3`）；对用户数据做在线权重更新不可回滚 | 等模型厂商把记忆能力商品化再谈对接 |
| 碰用户的密钥 | 密钥只走 `${VAR}` / env 插值，我们只读、只使用、不落盘、不进日志（`03-hosts-and-interfaces.md`） | 永不放松 |
| 通用知识库 / RAG 平台 | 只服务 agent 的长期记忆，不替代文档检索（`00-brief.md §4`） | 不做 |
| 自动记录一切 | 「有话说就记」是旧项目的病（`00-brief.md §4`） | 永不 |
| 第一年接通所有宿主 | MCP 是一等接口，先通 3 个（`00-brief.md §4`） | M3 |

**为什么这值得做**：长上下文确实杀死了「为了答对而检索」的论证，但没杀死检索——真正站得住的是成本/延迟，以及跨会话、跨宿主、可审计、可纠正（`02-evaluation.md §3`）。旧项目 131 轮注入 655 条指针、基础打开率 2.4%（`00-brief.md §2`），说明失败不在算法而在形态。

## 2. 组件边界

### 2.1 三层与依赖方向

```
core/      纯逻辑：数据模型、检索、打分、闸门判定、巩固决策、账本事件
   ↑                    ↑                      ↑
adapters/   宿主接口壳                data/     真相源与派生索引
```

依赖规则（**单向，反向禁止，进 lint**）：

- `core/` **零依赖**：不 import adapters、不 import 宿主 SDK、不直接读写文件系统、不发网络请求。它只吃数据结构、吐数据结构。
- `adapters/` 可以 import `core/`，以及各自的宿主 SDK。**adapters 之间不许互相 import**。
- `data/` 是纯文本目录，不是代码包；只有 `core/` 通过注入进来的 `store` 接口访问它，索引只是可重建的派生物。
- 任何一门语言实现都要能通过同一套 `core` 行为测试（一致性测试向量随包发布）。

### 2.2 目录草案

> 下面是**目标目录**，不是当前仓库布局。当前是单包 `src/`：`src/core`、`src/store`、`src/gate`、`src/mcp`、`src/import`、`bin/memory`；`packages/core`、`adapters/`、`consolidate/`、`serve` 等尚未拆分/实现。`core` / `adapters` 是逻辑分层，不是物理包。

```
memory-service/
├─ packages/
│  ├─ core/                 # 零依赖纯逻辑（npm: @yffto/memory-core）
│  │  ├─ model/             # 记录类型、frontmatter 解析、schema 版本与迁移
│  │  ├─ gate/              # 写入闸门：去重、价值、信任分级、fail-closed 检查
│  │  ├─ retrieve/          # BM25/词法 → 向量 → 融合 → 预算裁剪 → 拒答判定
│  │  ├─ score/             # 三因子打分、指数衰减、命中恢复、晋升/降级
│  │  ├─ consolidate/       # 巩固决策（去重/合并/摘要/时效化）产出 operation 列表
│  │  └─ ledger/            # 事件模型与口径定义（hit/injected/used/opened 四个独立事件）
│  ├─ adapters/
│  │  ├─ mcp/               # Dual-era MCP server（stdio 薄壳 + 常驻核心两种载体共用）
│  │  ├─ dsh-plugin/        # DSH 插件壳（薄，不直接写文件）
│  │  └─ cli/               # memory recall|remember|consolidate|forget|explain|doctor
│  ├─ eval/                 # 评测跑分器与题集（与 core 同级，不许被 core import）
│  └─ import-engramory/     # 旧库导入器（一次性，不进运行时依赖）
├─ suite/core-30-v1/        # 30 条任务 + 最小语料快照
├─ data/                    # 运行时数据（默认 ~/memory/<product>/，与代码分离）
└─ docs/
```

`data/` 草案（详见 §3）：

```
notes/<id>.md        <!-- 一条事实一个 md 文件：真相源 -->
index/               <!-- 全部是生成物，删掉能重建：ledger.jsonl（追加型事件日志）+ bm25/ vec/ entities.json -->
runs/<run-id>.json   <!-- recall receipt（已实现：不含正文，只有 hash）；巩固 receipt（目标：含 .diff.jsonl，可回放、可撤销） -->
.engramory-recall.jsonl   <!-- 旧库账本：只读挂载当评测输入（02-evaluation.md §4.8） -->
```

**代价**：三层分离让「加一个宿主」变成写一个薄壳，但也让每次改动都得跨包联调；`core` 零依赖意味着文件系统、时间、随机数、模型调用全部要注入（多写一堆接口）。**什么情况下该换**：如果到 M2 结束 `core` 里出现了第二处「为了适配某个宿主而加的分支」，说明边界画错了，该按能力（读/写/巩固）而不是按层重切。

## 3. 数据模型

### 3.1 一条事实一个 markdown 文件 + 索引

沿用旧系统已验证的形态（`00-brief.md §9` 的倾向，以及 Anthropic memory tool 把真相源放在客户端纯文件目录的事实，见 `01-landscape-systems.md`），但**索引改为生成物**。

```markdown
---
schema: memory.note/1
id: 01J8QK7M4P2V6N3R8T5W9XYZAB     # ULID，时间有序，写入即定，永不变
scope: project:github.com/yffto/yffto   # 或 user
kind: semantic                     # core|semantic|episodic|procedural（CoALA 四分类）
trust: user_stated                 # user_stated|system_derived|external
provenance:
  written_by: mcp:user               # 谁写的：mcp:user | cli:import | consolidator:v1
  source_ref: "session:2026-10-17/dsh#turn-42"
  derived_from: []                   # 若来自巩固：被合并/被摘要的 note id 列表
valid_from: 2026-10-17T02:56:53+08:00
valid_to: null
supersedes: []
superseded_by: null
confidence: 0.9
verify_after: 2027-04-17              # 到点进体检队列，不自动删除
tags: [preference, tooling]
aliases: [别名一, 别名二]          # 可选；作者给的同义说法，只参与身份核对（共现），不进 postings、不参与打分
---

用户要求：给 agent 用的记忆服务默认零 API 成本也能跑；语义检索是可选增强。
```

索引是 `notes/` 的纯函数：`index = f(notes)`。删掉 `index/` 只损失时间，不损失事实。这条是所有可审计性的前提。

### 3.1.1 索引是**分层路由**，不是一张平铺的清单（M2 落定）

旧系统（以及本项目的 M1）把索引做成一屏「一行一条指针」。这条路有一个致命的容量：`MEMORY.md` 被 200 行 / 25KB 盯着，而一行只能放一条笔记。M2 把真实旧库导进来之后的实测是：

| | 笔记数 | 索引列得出的 | `status` 报的 |
|---|---|---|---|
| 平铺索引（M1） | 1321 | **127** | `indexHidden: 1194` |
| 分层路由（M2） | 1321 | **1321** | `indexHidden: 0` |

**127/1321 —— 也就是说「读索引」这条路九成是瞎的。** 检索面一直是好的（它全扫 `notes/`），坏掉的只有「读索引」：人和 agent 翻开 `MEMORY.md` 会以为库里只有 127 篇，剩下的 1194 篇**在索引里不存在**。这不是「索引有点旧」，是**沉默地告诉读者一半的库不存在**。

方案的关键认识是一条不对称：**索引的行数有上限，而索引的文件数没有。** 于是把「一行一条记录」换成「一行一个主题组」：

```
index/MEMORY.md              路由层：一行一个主题组（真实库 72 行 / 7.5KB）
index/groups/<nnn>-<组名>.md 清单层：一组一行指针（每文件 ≤ 400 行，超过分页不截断）
```

容量算一下就清楚：路由层一行约 40 字节、装得下约 190 个组；清单层每个文件装 400 条 ⇒ **约 190 × 400 = 76000 条**，而且每一篇都有**一条能走到的路**。这是「换维度」而不是「压缩」——把指针压得更短只能多装几十条，改不动「上限 200 条 vs 有 1321 条」这个量级差。

组的定义：笔记 id 里第一个 `#` 之前的部分（`reference-x#137` → `reference-x`；真实库 1321 篇只有 72 个这样的前缀）。为什么按 id 而不是按 `kind`/`tag`：`kind` 只有 4 个组、每组几百条，路由层装得下但清单层一个文件装不下，等于把问题往下推一层；id 前缀是人自己写文件时形成的**天然主题**，组数与组内条数都落在「人扫得动」的量级。

**为什么没有采用原定的「consolidate 把碎片合成整篇」那一半。** 架构文档早先给的方向是「先合并碎片笔记，再分层索引」。把真实库读进来之后，这个前提不成立，理由是可验证的：

- 1164/1321 集中在 7 个大组（最大一组 200 篇），它们**不是同一件事的碎片**，而是同名主题的高频重复记录（`…#1` 到 `…#200`）。合并它们 = 把 200 条记录压成 1 条，丢的是内容不是重复。
- 真正该合并的（同主题的 3–4 条改写）合起来省几十行，救不了 1194 的缺口 —— 量级对不上。
- 最要紧的是：consolidate 会**改真相源**（`notes/`）。为了让索引好看去改写记忆内容，是把「生成物装不下」的问题转嫁给唯一手可编辑的真源。这个交换不划算。

所以分层索引只动 `index/`，`notes/` 一个字不动。巩固（§4.2）仍然要做，但它的理由是内容质量与时效，**不是给索引腾地方**。

**诚实边界**（这些也是 `tabellio index --json` 要报的账）：路由层消除的是**结构性**盲区（前 N 条可见、其余不存在）。它不消除**分组**盲区：组数超过路由预算时会把相邻小组打包成中间层（digest，文件里仍列出子组真名），打包到底还装不下就明着报 `hidden` / `unreachable`，**不静默截断**。路由层的字节维度同样要自觉遵守：生成器先削（丢最小组）再交给闸门，否则闸门拒写会让库从「索引不全」直接退化成「没有索引」——旧项目正是这么丢过一次索引。

**为什么够用**：① `cat` 得出的东西才谈得上「用户拥有」；② 文件粒度天然对齐旧库的索引上限实践（`01-landscape-systems.md` 引 Claude Code auto memory 的硬限制）——但上限只该约束**单个文件**，不该约束「一个库能被索引多少条」，分层就是把这两件事拆开；③ 跨宿主共享同一批文件比跨宿主同步数据库简单一个数量级；④ git diff 就是审计记录。


**什么时候不够用**：① 记录数进万级后「目录扫描 + 词法索引重建」会变慢，缓解是索引持久化 + 增量更新——**这不是现在就换数据库的理由**；② 需要双时态多跳图查询（「三个月前我认为 A，后来因为 B 改成 C」这类遍历）时，文件 + 邻接索引的表达力不如时序图，**到那时再引入图，且只作为 `index/` 的一种，不是真相源**（Zep/Graphiti 用 Neo4j 当真相源，我们不跟，见 `01-landscape-systems.md`）。另外，单条事实**必须 ≤ 200 token / ≤ 400 字核心档**（`04-cost-model.md` 省钱清单第 13 条），超长内容写入时切分为多条，否则重排成本按整篇计。

### 3.2 生命周期状态

`draft → active → stale → superseded → archived`（`archived` 不硬删，只从默认检索面消失）。

- 进入 `stale`：`recency` 分数连续 K 轮低于阈值且从未被注入过（默认 K 与阈值可配，规则形状照抄 `05-agi-direction.md §4.3`）。
- 进入 `superseded`：被新记录在 (subject, predicate) 上取代，**写 `superseded_by` 而不是删除**。
- 进入 `archived`：低置信 + 从未命中 + 无来源（这一条旧项目缺，是 200 行索引膨胀的根因之一，见 `05-agi-direction.md §4.2`）。

### 3.3 时间与冲突

四个字段把「时间」这件事说清：`valid_from` / `valid_to` / `supersedes[]` / `superseded_by`。

- 冲突规则（确定性，不需要模型）：新记录与旧记录同一 `(subject, predicate)` 且值不同 → 旧记录 `valid_to = now`、`superseded_by = 新 id`；**两条都留着**。
- 因为「用户 5-14 前偏好 Python，之后 TypeScript」与「用户偏好 TypeScript」是不同信息，服务必须能同时回答 **as-of** 查询与 **changed-since** 查询（`05-agi-direction.md §4.1`）。
- 已知会咬人的四个边界（清单来自 `05-agi-direction.md §5.2` 的 2026 年实践批评）：标签过滤被静默忽略、date-only as-of 解析到午夜、删后重建产生重复、时区混用。**这四条直接进评测用例**。

### 3.4 schema 版本与迁移

- 每个文件自带 `schema: memory.note/1`；读侧遇到更高版本**拒绝解释、原样透出**，不做「猜着解析」。
- 迁移是**离线批处理 + 可回滚**：`tabellio migrate --to 2 --dry-run` 先产 diff，落 `runs/migrate-<id>.diff.jsonl`，再原子替换；旧文件备份为 `notes/.v1-backup/`（保留到下一次迁移）。迁移脚本与索引重建脚本是同一类东西：**都不许在服务运行中改真相源**。
- 索引自带 `index_manifest.json` 记录构建时的 schema 版本、embedding 模型指纹、代码版本；指纹不匹配就重建（模型指纹绑索引这个做法来自 `01-landscape-systems.md` 里的 HippoRAG 2 实践）。

**代价**：文件即真相源 = 每次查询都要面对「文件可能是人手改坏的」。我们的对策是解析失败时 fail-closed（跳过该文件并记事件），代价是可能静默漏掉一条记忆；因此 `doctor` 必须把解析失败数当一等指标暴露。**什么时候该换**：如果 `doctor` 长期报告 >1% 文件解析失败，说明手改成本超过收益，该加「只有工具能写」的模式开关（默认仍开手改）。

## 4. 写入与巩固管线

### 4.1 热路径只追加（零 LLM）

```
用户/agent 调用 remember
  → gate 判定（确定性规则，无模型调用）
       ├─ scope 合法性        （越权写 user scope → deny）
       ├─ 去重               （同 scope 下 8-gram 重叠 > 阈值 → 返回 duplicate + 已有 id）
       ├─ 价值闸门           （寒暄/空/短于 4 字 → 静默 skip；「大多数轮次什么都不该记」）
       ├─ 信任分级           （外部内容 → trust: external，且 kind 不得为 procedural）
       └─ fail-closed 检查   （外部内容试图成为规则/指令 → deny）
  → 追加一条 note 文件（原子写：临时文件 + rename）+ 一条 append 事件
  → 返回 { id, status: "stored" | "duplicate" | "skipped" | "denied", reason }
```

热路径**不做**：不改旧记录、不做冲突消解、不合并、不摘要、不调模型。三条独立证据指向同一结论（mem0 2026-04 起单次 LLM 调用只 ADD；Letta 把整理放 sleep-time；dsh-mneme 冲突冻结进人工队列），见 `01-landscape-systems.md`。

### 4.2 空闲期巩固（唯一的「改」入口；M2 已开工，当前有 `invalidate` / `archive` 与内容类提案层）

> **现状（2026-10-17）**：落地两种只动元数据的操作：`invalidate` 与 `archive`。`dry_run` 是默认值：只出计划，不落盘、不改库。
> `apply` 先写 `runs/<run>.plan.json`，再逐条改目标笔记：invalidate 写 `valid_to` / `superseded_by`；archive 只把 `status` 改成 `archived`（**不写** `valid_to` / `superseded_by`）。正文逐字节不动，最后写 `runs/<run>.json`；回执写不进去就回滚已改字段。`consolidate --undo <run>` 先全量预检再恢复元数据，写 `runs/<run>.undo.json`。
> archive 必须由人显式点名，不是自动衰减；默认检索面（含当前 `as_of` 路径）会排除 `archived`，而 invalidate 的旧记录仍可按 `as_of` 查到。
> `merge` / `summarize` / `promote` 只做到**提案层**：由人显式点名源 id，生成合并稿 / 抽取式摘要 / 候选规则脚手架，`dry_run:true`、`apply_supported:false`、`would_write:false`，不写 run、不写 note、不写 candidates。执行层、自动衰减、`diff.jsonl`、replay、`forget`、后台自动巩固**都还没实现**。

触发：显式 `consolidate`（已实现）；空闲期后台或每晚一次（未实现，可关）。巩固分两步，**决策与执行分离**：

```
consolidate(dry_run=true)  → 产出 operations[]（纯决策，不落盘）
consolidate(apply=true)    → 写 runs/<id>.plan.json → 逐条执行 → 写 runs/<id>.json
```

operation 类型与护栏：

| operation | 动作 | 护栏 |
|---|---|---|
| `merge` 🟡 | N 条同类 → 1 条，原记录 `archived` + `derived_from` 指回 | 原文永不出库；合并结果正文里必须能追到源 id。当前只出提案草稿，不执行 |
| `summarize` 🟡 | 长记录 → 摘要，摘要进新 note，原文降为 `archived` | 摘要必须带 `source_ref`；只允许压缩，不允许新增事实。当前只出抽取式提案 |
| `invalidate` ✅ | 冲突胜出方 → 旧记录 `valid_to=now` + `superseded_by=胜出方` | **只写元数据，不改旧记录正文**（Graphiti 式失效而非删除）；`as_of` 仍可查 |
| `promote` 🟡 | 同类事实 ≥ N 条且覆盖 ≥ M 个时间点 → 候选规则 | **只产候选**，落 `notes/candidates/`，要人确认才进主库。当前提案草稿已在内存里指向该路径 |
| `archive` ✅ | 显式点名仍 `active`、时间有效的记录 → `status=archived` | 不删除，不写 `valid_to` / `superseded_by`；默认检索面（含 `as_of`）排除；`undo` 只恢复 `status` |

> 🟡 = **只有提案层**，没有执行层。提案读库、出草稿，但不写 `runs/`、不写 `notes/`、不写 `notes/candidates/`；
> 因此它没有 receipt（没写东西就没有账），也不能 `--undo`。执行层落地时，receipt / 撤销 / 原文链接必须按下面护栏补齐。

**护栏（写进代码，不靠模型自觉）**：

1. **巩固绝不能悄悄改事实**：任何写入都必须留下 receipt，receipt 里含操作前后的元数据、正文 hash（sha256）与字段 diff；没有 receipt 的写入被视为 bug。当前 `invalidate` / `archive` 的回执已满足这条；内容类提案不写库，所以没有 receipt——执行层实现时必须补。`diff.jsonl` 未实现。
2. **可回放**（未实现）：`consolidate --replay runs/<id>.json` 能在库的副本上重放出同一结果；跑不出同一结果即视为不可信，撤销该 run。
3. **可撤销** ✅：`consolidate --undo <run>` 把该 run 的所有操作逆序回退；先全量预检，任何一条冲突就整单拒绝，不做部分撤销。因为我们从不物理删除，撤销总是可能的。
4. **原文优先**：检索命中一条被 `summarize` 覆盖的记录时，默认返回摘要 + 原文链接；用户要原文时永远取得到。
5. **一次 run 的改动量上限** ✅：`allowed = max(1, floor(扫描条数 × max_change_ratio))`，默认 0.05；超限整单中止、一条不动。小库至少允许 1 条，否则 10 条库上 `floor(0.5)=0` 永远熔断。

**代价**：决策/执行分离 + receipt 让巩固代码量至少翻倍，且「原文永不删除」会让库持续变大。**什么时候该换**：如果库年增长 >50 万条或单次巩固 >10 分钟，说明文件粒度太细，该引入「合卷」（多个相关事实合并为一个文件、内部再分级），但**不放弃 receipt 与可撤销**——那两条是审计性，不可谈判。

## 5. 检索

### 5.1 默认 pull，push 只留极小核心

- **默认形态**：宿主 agent 主动调 `recall`。行业事实标准就是 pull（mem0/Letta/Claude memory tool/MCP memory/Basic Memory 全是主动调一次），旧项目 push 指针的打开率是少数派且已被自己的数据证伪（`01-landscape-systems.md`）。
- **always-on 极小核心**：仅 `kind: core`（身份/硬偏好），**≤ 400 字**，可关（`00-brief.md §6` 架构原则 1）。这个量级与 Claude Code auto memory「只注入首 200 行 / 25KB」的官方硬限制同数量级，数字有出处（`01-landscape-systems.md`）。
- **push 不下判断**：推送只发**内容**（不是指针）——旧项目的教训是「注入指针 = 把『要不要读』的判断外包给宿主模型」，2.4% 打开率是接口形状造成的（`05-agi-direction.md §7`）。指针模式降级为「台账放不下时」的兜底通道。

### 5.2 分层热度 + 硬预算

检索顺序（每一层都可能直接返回，后层是增强不是必需）：

1. **词法**（BM25 + 同义扩展 + 中英文归一化）：默认档、零成本、零依赖。旧项目实测 103ms / 71 篇（`03-hosts-and-interfaces.md` 引 `dsh-engramory-recall/docs/release.md`），说明这个量级纯词法完全够快。
2. **本地向量**（若检测到本地端点，如 `http://127.0.0.1:11434`）：`Qwen3-Embedding-0.6B` 真库 hit@1 68.4% vs 云端 `Embedding-3` 74.7%，差约 6pt，可用（`04-cost-model.md`）。
3. **重排**（默认**关**）：只喂摘要，候选池默认 10、上限 20，单篇 ≤200 token。

**硬预算**：调用方传 `budget_tokens`，服务端裁剪并**说明裁掉了什么**（这一条来自 `00-brief.md §6` 原则 5）。裁剪顺序：先丢 `episodic`、再丢低 trust、最后才丢 `core`。

**三因子打分**（照抄 Generative Agents 形状，确定性、零模型成本，`05-agi-direction.md §4.3`）：

```
score = w1*importance + w2*recency + w3*relevance
recency = exp(-Δdays / τ)          # τ 默认 30 天；被命中时抬高 base（MemoryBank 式恢复）
```

### 5.3 拒答路径（一等公民）

没有足够证据时必须能说「不知道」。返回 `status: "insufficient_evidence"` 而不是拼凑最相关的三条。理由（`05-agi-direction.md §5.2`）：自信地用陈旧记忆作答比说「我不知道」更糟；弃答在所有公开基准里被系统性低估。

拒答判定必须**可解释**：返回 `why_not`（最高分低于阈值 / 只有 external 低信任来源 / 命中的记录都已 `valid_to` 过期 / 命中之间值互相冲突且无法用时间排序）。拒答率是评测的一等指标，用它去调阈值，不要凭感觉。

### 5.4 命中判定的口径（M2 落定，代码在 `src/core/recall.js` + `src/core/bm25.js`）

这一段是把「什么样的命中算数」从代码注释里搬上来。**口径写在文档里，代码是实现**；两者不一致时以本文档为准，改口径要连文档一起改。

**① 覆盖率闸门（`score.coverage`，M1 就有）**

```
coverage(doc) = 该文档某个 400 字桶里命中的词项权重之和 / 整条查询的权重之和
权重 = 词项的 idf × 它在查询里的出现权重（bridge 词 0.6、单字 0.5）
MIN_COVERAGE = 0.6（默认，可被 --min-coverage 覆盖）
逐桶算、取**最大**：一条长笔记里只有一段真正相关时，取 max 而不是全文平均，
    否则「一句话的答案埋在一篇 4000 字的笔记里」会被自己的长度摊薄成不达标。
总权重只算**索引里存在的**查询词项：查不到的词项贡献 0，不参与分母。
```

**② 证据性闸门（`no_informative_term`，M2 新增，与 ① 是「且」的关系）**

```
INFORMATIVE_DF_RATIO = 0.05        # 词项的证据线：df / 语料条数 ≤ 0.05 才算「有信息量」
INFORMATIVE_DF_FLOOR_DOCS = 64     # 绝对词频地板：df ≤ 64 也算「有信息量」（M4 新增）
查询的全部词项都**不是**有信息量的（都太常见）→ 拒答，reason = 'no_informative_term'。
判据是**或**：df ≤ 地板（绝对词频，与语料规模无关）**或** df/n ≤ 0.05（比例，管大库）。
```

M4 之前判据只有比例那一半，并且用 `INFORMATIVE_MIN_DOCS = 200` 把闸门在 200 篇以下整个关掉。那版是坏的：它让闸门**要么全关、要么在小语料上全拒**，中间没有过渡（实测见 §5.5，200 篇档可答题 `recall@5` 0.0%）。现在这个常量已不参与判定（`src/core/bm25.js` 仍导出它只为兼容旧引用）。

为什么加绝对词频这一支：`df/n` 的分母是语料规模，而「一个词项是不是证据」本该由**它自己**在库里出现的绝对次数决定。「同一句话被抄进上百篇笔记」是结构性的信号，跟库里有 50 篇还是 5000 篇无关；反过来，小库恰恰最容易被 n 放大误判 —— n=50 时服务名只落在 10 篇笔记里，按比例算是 20% 的「常见词」，可那 10 篇是 10 篇**不同**的笔记。地板 64 的取法：它在真库尺度（1321 篇）上**低于**比例线的分界 `0.05 × 1321 = 66.05`，所以真库行为逐字不变；它又在 `n < 1280` 时比比例线宽松，于是小库不再整条拒答（`64 / 1280 = 5%`，两条线正好在 1280 篇交叉）。

为什么小语料上不能退化成「什么都拒」：拒答是**破坏性**的 —— 少答一次的代价比多答一次更高（用户看到的是「它说它不知道，可我明明记过」）。闸门的用途是拦「整条查询只有常见词」这一个已确诊的病灶（下面的例子），不是为了收紧而收紧；在它拦不住病灶的规模上，它就不该有发言权。

为什么需要 ②：覆盖率闸门有一个结构性的洞。当**整条查询的所有词项**都是常用词时，`totalMass` 本身就很小，于是「命中了其中一个常用词」就很容易把 coverage 顶到 1.0。实测（真实库 1321 篇）：

```
memory recall --query "量子色动力学里的胶子禁闭"
  → 切词：量子 子色 色动 动力 力学 学里 [里的] 的胶 胶子 子禁 禁闭
  → 只有「里的」在语料里存在（df 96/1321 = 0.073）⇒ 所有含「里的」的文档 coverage = 1.000
  → 92 条命中、refused:false、top score 0.646 —— 库里没有任何一条与量子色动力学有关
```

**③ 修在切词层，不修在打分层（M1 的教训）**

同一个洞还有第二个成因，比 ② 更常见：切词器把相邻二字组一律生成，于是**跨词边界**会拼出并不存在的词 —— 「闸门」+「的」→ `门的`，「闸门」+「的默认值」→ `的默`。这些碎片是**高频**的，它们的存在让「整条查询都由常用词组成」这件事变得更常见。

M1 曾经试过在**打分层**修：给高 df 词项按 idf 打折。结果是真答案被一起压掉了 —— `recall@5` 从 0.844 掉到 0.563，已回退。**教训：不要把「这个词项是不是证据」和「这个词项有多重要」混成一个连续折扣。** 前者是二值的、属于切词与词表，后者才是权重。

M2 的正解落在切词层（`src/core/tokenize.js`）：

- **结构助词当边界**：`CJK_BOUNDARY_CHARS = {的, 了, 是, 在, 和, 与}` —— 在这六个字处把 CJK 串**断开**再取二元组，于是 `门的` / `里的` / `的数` / `和与` 这类碎片**根本不会被生成**（不是事后过滤，是不生成）。断开后只剩边界字的 run（如「的的」）整段丢弃：那种 run 没有内容。
- 集合刻意保持**最小**（六个字），每加一个都要有「不加就出假命中」的实例。改前实测：`tokenize('闸门的默认值是什么')` → `[闸门, 门的, 的默, 默认, 认值, 是什, 什么]`；改后 → `[闸门, 默认, 认值, 什么]`。
- **为什么是「断开 + 丢弃」而不是「降权」**：`的 / 了 / 是` 这类字在中文里的出现频率与「是不是证据」无关，它们**从不**是内容词。降权只是把假命中压小，仍然让它占着查询信息量的分母；丢弃才是把「跨词碎片根本不成立」说清楚。
- **明确没做**：没有把实词也切碎（`数据库` → `数据 / 据库` 这种相邻二字仍然保留）。那是另一件事，会动摇已经跑通的召回；这一期只处理「跨结构助词的碎片」这一种已确诊的病灶。也没有引入词表/最长匹配 —— 实测不需要（上表 `recall@5` 一条没掉就说明了）。

**④ 这一改动的实测账（`node bench/run-eval.mjs --same-corpus`，同一语料前后对比）**

| 指标 | 改前 | 改后 | 阈值 | 说明 |
|---|---|---|---|---|
| `recall@5` | 0.844 | **0.844** | ≥ 0.80 | 真答案一条都没被压掉（这是 M1 那次失败的反面） |
| `correct_refusal_rate` | 0.125 | **0.750** | ≥ 0.75 | 从「几乎不拒答」到刚好达标 |
| `injected_tokens_mean` | 299.9 | **310.0** | ≤ 500 | 略升：多出来的拒答不注入上下文 |
| `token_efficiency` | 2.251 | **2.177** | ≥ 2.0 | 略降，仍在阈值内 |

拒答率能一次涨 0.625，主因是**切词层**：任务集里的拒答题问的是「库里没有的值」，而改前它们能靠 `的数` / `存的` 这类跨词碎片把 coverage 顶到门槛以上（假命中）；碎片不再生成之后，这些题自然落回拒答。`correct_refusal_rate` 在语料 51 条时**不**受 ② 影响（② 在 <200 条语料上关闭），所以涨的这 0.625 全部来自切词层 —— 这也是「口径与实现要能对得上账」的一个例子。

**⑤ 证据性闸门在评测语料（51 篇）上失效但不出声 —— 这条现在是实测的**：M4 把闸门的规模开关拿掉之后，`core-30-v1` 的 52 道题逐题查过 `informative_terms`，**没有一道题是 0 个证据词**（52/52 都有证据词），所以判据 1 的 `recall@5` 0.844 与 `correct_refusal_rate` 0.80 都不受影响。改前改后 `node bench/run-eval.mjs --same-corpus` 的这两个数逐位相同。口径上与 ② 无关这件事没变（51 篇上拒答率的 0.625 涨幅仍然全部来自切词层，见 ④），变的是「闸门在 51 篇上是关着的」这个**机制**描述 —— 它现在是开着的，只是恰好不对这套题发言。

**⑥ 明确没做的事**：没有给覆盖率闸门加「稀有词计数」这类新阈值。在 `core-30-v1` 的 51 篇语料上逐题算过：**每一个可答题的最小 df 比都是 1/51 或 2/51**，所以「至少一个稀有词」这种判据会把可答题和拒答题一起放行，等于没加。加了只会多一层永远不触发的代码。
覆盖率闸门的机制一个字没改（`MIN_COVERAGE = 0.6`、逐 400 字桶取最大、分母只算索引里存在的词项）—— 改的是**喂给它的词项**。

**代价**：默认纯词法 = 召回质量比语义检索低约 6pt（hit@1 口径，`04-cost-model.md`）；拒答路径会让「记忆明明有过但被答成不知道」的情况变多。**什么时候该换**：如果判据 1 的 `recall@5` 在纯词法档低于 0.80 而开向量后达标，说明词法档不该做默认档——那就把「本地向量」提到默认（代价是用户必须跑一个本地端点，见 `04-cost-model.md` 的取舍）。

### 5.5 常量扫描：`MIN_COVERAGE` / `INFORMATIVE_*` 在 50–2000 篇上的曲线（M3 新增）

② 的两个常量（`INFORMATIVE_DF_RATIO = 0.05`、`INFORMATIVE_MIN_DOCS = 200`）此前只有两个观测点：`core-30-v1` 的 51 篇（闸门关闭）与真实库的 1321 篇（闸门开启）。**中间量级没人测过**，而闸门恰好是在 200 这个刻度上从「关」跳到「开」的。装置 `bench/sweep.mjs` 补这一段：合成语料 50 / 200 / 500 / 1000 / 2000 篇 × 多组查询（可答题 80 条 = 逐字 / 换词 / 只给名字三档 + 不可答题 8 条），扫覆盖率阈值与 df 比阈值，每格算「可答题 `recall@5` / 不可答题拒答率」。

命令：`node bench/sweep.mjs`（默认五档全扫，约 20 秒；`--json` 出机器可读，`--docs 50,200` 收窄）。

**证据性闸门（df/n）在语料刚过 200 篇时是坏的 —— 这是本次扫描的主要发现：**

| 语料 | 关（不启用 ②） | df/n ≤ 0.01 | df/n ≤ 0.02 | **df/n ≤ 0.05（生产值）** | df/n ≤ 0.1 | df/n ≤ 0.2 |
|---|---|---|---|---|---|---|
| 50 篇（闸门关闭） | 80.0% / 0.0% | 80.0% / 0.0% | 80.0% / 0.0% | 80.0% / 0.0% | 80.0% / 0.0% | 80.0% / 0.0% |
| 200 篇 | 80.0% / 0.0% | 0.0% / 100.0% | 0.0% / 87.5% | **0.0% / 87.5%** | 80.0% / 0.0% | 80.0% / 0.0% |
| 500 篇 | 80.0% / 0.0% | 0.0% / 100.0% | 0.0% / 100.0% | 80.0% / 62.5% | 80.0% / 0.0% | 80.0% / 0.0% |
| 1000 篇 | 80.0% / 0.0% | 0.0% / 100.0% | 70.0% / 62.5% | 80.0% / 62.5% | 80.0% / 0.0% | 80.0% / 0.0% |
| 2000 篇 | 80.0% / 0.0% | 70.0% / 62.5% | **80.0% / 62.5%** | **80.0% / 62.5%** | 80.0% / 0.0% | 80.0% / 0.0% |

> **这张表读召回那一列是准的，读拒答率那一列整体偏低。** M4 做产物检查时发现装置自己的覆盖率算错了（只取分数最高的那个桶、且没乘词项 idf，见 §5.5.1 末段），修好之后同一批格子的拒答率会抬高（例如 50 篇「关」这一格是 100.0% 而不是 0.0%）。**结论不变、还更强**：修好之后全网格 1960 格里 `recall ≥ 0.80` 且拒答 `≥ 0.75` 的格子是 **0 个**。上表保留 M3 当时的读数，因为「闸门一开就在 200 篇上全拒」这个主发现两版装置都能复现。

读法与结论：

1. **闸门一开就过头**。200 篇上生产值（0.05）把**可答题全部拒掉**（`recall@5` 0.0%），而拒答率 87.5%；连保守到 0.01 也一样。行为直到 2000 篇才回到「可答题一条不丢 + 拒答 62.5%」。这个区间里 ② 不是「多拒几条」，是**整个检索不可用**。
2. **「保持召回 ≥ 0.95」在五个档位上都没有可行解**：任一阈值要么丢可答题，要么一个都不拒（`--json` 的 `recommend.feasible` 会照实报 0，不硬凑建议值）。所以这里给不出一个「更对的常量」，只能给出**安全区**：`INFORMATIVE_DF_RATIO ∈ [0.02, 0.05]`、语料 **≥ 1000 篇**才启用；`INFORMATIVE_MIN_DOCS` 现在的 200 是个**下界偏低**的值。
3. **生产值在 1000 篇上恰好落进安全区**（0.05 / 80.0% / 62.5%），这就是 `INFORMATIVE_MIN_DOCS = 200` 至今没暴露问题的原因：真实库 1321 篇，已经在安全区里。**但它离悬崖只有两倍距离**——语料从 1321 掉到 500（用户清理一批旧笔记是完全正常的操作）就会踏进「全拒」区间。这条要在 M4 之前处理，处理方式见下。
4. **明确没测出来的东西**：覆盖率闸门在这套合成语料上**完全不动**（每一档、每个阈值都是 80.0% / 0.0%）。原因是合成语料的查询词与 gold 笔记**逐字同源**，gold 的 coverage 中位数在 50 / 200 / 2000 三档上都是 **1.00**，而不可答题的最优覆盖也到 1.00 —— 这个夹具分不开两类题，所以它**不能**用来给 `MIN_COVERAGE` 定值，只能说明「0.3–0.8 之间不敏感」。要给覆盖率定值，得用**换词更狠**的查询（把「每天几点」说成「多久跑一次」）或真实库语料，这是 M4 的活。

**建议值（写成常量而不是口号）**：把 ② 的启用条件从 `n >= 200` 抬到 `n >= 1000`，`INFORMATIVE_DF_RATIO` 由 0.05 收到 0.02。理由不是「更严格」，而是**在安全区里取靠中位的一个点**：0.02 在 1000 篇上仍保住 70% 召回、2000 篇上 80%，而 0.05 在 500 篇上就已经把可答题全拒。M3 不动生产常量（判据 1 在 51 篇语料上不受影响，动它没有可用的验收装置），把改动留给 M4 连同「覆盖率闸门的换词夹具」一起做。

### 5.5.1 M4 的修法与五档前后对照（`INFORMATIVE_MIN_DOCS` → `INFORMATIVE_DF_FLOOR_DOCS`）

M3 那条建议（抬门槛到 1000 + 比例收到 0.02）**没有被采纳**：它只是把悬崖推远，没有拆掉悬崖 —— 判据仍然是 `df/n`，仍然由语料规模决定，所以换个规模（比如用户把 1321 篇清到 999 篇）就会再撞一次。M4 改的是**机制**：判据换成「绝对词频地板 **或** 比例」的或关系（口径与理由见 §5.4 ②），`INFORMATIVE_MIN_DOCS` 这个「按语料规模开关闸门」的常量**取消**（保留导出仅为兼容）。

随之改的还有 `queryInfo.informativeGateEnabled` 的语义。它原来报的是「语料够不够大」（`n >= INFORMATIVE_MIN_DOCS`），现在报的是「**这道闸这次有没有改变判定**」—— 即过滤时**真的删掉过词项**才报 `true`。两种情况下报 `false`：候选词项在库里全都不存在（`df = 0`，那是选择层的事），或者存在的词项全都过闸（小语料上 `df ≤ 地板` 一一放行）。报 `true` 而实际一个词项都没删，会把成因完全不同的两种拒答 —— 「选择层一个词项都没选中」与「选中的词项全是常见词」—— 混成同一个 `no_informative_term`，而这两种的修法完全不同（前者怪切词/`MIN_DF_DOCS`，后者才是这道闸在说话）。这也是把闸门从「按规模开关」改成「按判据生效」时唯一一处**必须跟着改**的对外行为。

`bench/sweep.mjs` 的 df 比曲线现在带一条「地板」轴（`dfFloorPoints`，`0` = 修复前的纯比例口径，`3200` = 比任何一档都大 = 闸门关掉），所以修复前的读数可以在同一台装置上重现。生产口径扫描结果（每格 = 可答题 `recall@5` / 不可答题拒答率）：

| 语料 | 修复前（比例 0.05，`n ≥ 200` 才启用） | 修复后（比例 0.05 **或** df ≤ 64） | 生产路径实测（修复后） |
|---|---|---|---|
| 50 篇 | 0.0% / 100.0%（闸门没启用，证据词集合 = 全部命中词） | 80.0% / 0.0% | 80.0% / 0.0% |
| 200 篇 | **0.0% / 87.5%**（可答题全被拒） | **80.0% / 0.0%** | **80.0% / 0.0%** |
| 500 篇 | 80.0% / 62.5% | 80.0% / 0.0% | 80.0% / 0.0% |
| 1000 篇 | 80.0% / 62.5% | 80.0% / 62.5% | 80.0% / 62.5% |
| 2000 篇 | 80.0% / 62.5% | 80.0% / 62.5% | 80.0% / 62.5% |

第三列是**判据本身的自检**，不是装饰：拿 `src/core/recall.js` 的 `recall()`（生产真实路径）在同一批合成语料上逐题跑一遍，与装置的逐题判定对照 —— 五档合计 **580/580 道题判定逐题相同**（M4 修掉装置覆盖率算法之后从 1/580 收敛到 0/580）。**装置量的是生产的行为，不是它自己的一厢情愿** —— 这条对照已经写进 `test/bench-sweep.test.mjs`。

修复前那一列现在能在同一台装置上重现（`dfFloorPoints` 取 0 就是纯比例口径）：只有 200 篇那一格曾由 M3 用**装置强制打开闸门**量出来（那时装置不会在生产关闭闸门的规模上量生产），其余四格是「修复前的判据 + 生产覆盖率分母」的装置读数，与生产在修复前的真实行为对得上（n≥200 时闸门过头：200 篇全拒；≥500 篇 80.0% / 62.5%）。生产在修复前的另一段行为是 **n<200 时闸门失效**（答得出题、一条都不拒）。两段都不是好的，这也正是「不能只调数字」的理由。

**装置本身也修了一处（要记账）**：`bench/sweep.mjs` 的 `coveredIds()` 原来按「`Σ 命中词权重`（不乘 idf）」算覆盖率，而且**只取分数最高的那个桶**；生产的 `scoreDocs()` 是「`mass = Σ qWeight·tf(k1+1)/(tf+k1·norm)`，分母 = 证据词的 idf×权重之和」，笔记层再由 `aggregateByNote()` 取**各桶覆盖率的最大值**。两处差异叠起来让装置**系统性低估覆盖率**：产物检查抓到 `Cinderbay 的连接池最多几个？` 装置判「无合格命中」（eligible=0）而生产判 12 条合格；逐题对账显示 50 篇档有 25/68 道题判定不同。按生产公式重写之后是 0/580。**教训**：装置里凡是「重写一遍生产口径」的地方（这里、`idfOf`、闸门判据）都是同一类风险 —— 它们不会因为参数扫描而暴露，只会把「装置结论 ≠ 生产行为」悄悄写进报告；所以每加一条这样的重写，就要配一条与生产真路径的逐题对账（现在 `test/bench-sweep.test.mjs` 有）。

五档验收线（每档 `recall@5 ≥ 0.80` 且拒答率 `≥ 0.75`）的结论：

1. **召回这一半五档全过**：修复后每一档（装置与生产两条路径）都是 80.0%，而修复前 200 篇档是 0.0%（可答题被整条拒掉）。
2. **拒答这一半五档一个都没过**（五档分别是 0.0% / 0.0% / 0.0% / 62.5% / 62.5%：50–500 篇档 0/8 条不可答题被拒，1000/2000 篇档 5/8 条）。8 条不可答题每题占 12.5%，所以 `≥ 0.75` 要拒掉 6/8 —— 差的那一条就是全部差距。**这条验收线在这套夹具上无解**：修好装置之后把 5 档 × 7 个覆盖率 × 7 个 df 比 × 7 个地板共 **1960 格**全扫了一遍，`recall ≥ 0.80` 且拒答 `≥ 0.75` 的格子是 **0 个**。原因不是修得不够，是夹具的结构决定的：8 条不可答题全是一个形状 —— 「服务名 + 一个通用词」（`Lumenpath 的命中率目标是多少？`），它们的 `coverage` 与可答题**完全不可分**（把覆盖率闸门关掉、逐题量 top-5 的最大覆盖率：五档上 8 条不可答题**全部是 1.000**，而 120 条可答题里最小的 12 条也**全部是 1.000** —— 两类题的覆盖率分布一模一样，夹具里没有任何阈值能把它们分开）。要拒掉它们只剩证据性闸门一条路：得把「服务名 + 通用词」这一档词全判成非证据，而那会把 36 道 `drop` 档可答题（形状完全相同）一起拒掉。CJK 切词在这里也帮不上忙：`命中率`→`命中/中率`、`总共`→`总共` 这些词项在库里 df=0，本身就进不了分母。**在这套夹具上，`recall ≥ 0.80` 与 `拒答率 ≥ 0.75` 是对同一条判据的相反要求**，不是两个可以分别满足的指标；要把验收线变成可满足的，得先改夹具（「判别词 df 不随语料增长」这件事本身不真实，真实库里一个知识点会被越写越多篇；不可答题也得换成**在库里有近邻但事实不同**的形状），不是改闸门。这条结论与 §5.5 第 4 点（M3 记的「覆盖率闸门在这套合成语料上完全不动」）是同一件事，M4 把它量成了逐题分布。
3. **判据 1 不受影响**：`node bench/run-eval.mjs --same-corpus` 的 `recall@5` 0.844、`correct_refusal_rate` 0.80、`injected_tokens_mean` 254.9 三项与改前逐位相同；52 道题里没有一道落到 `no_informative_term`（逐题查过 `informative_terms`，52/52 都非空）。

回归用例：`test/bench-sweep.test.mjs` 新增「小语料不许全拒 —— 200 篇档生产口径必须还能答题」（五档逐档跑生产口径，`recall@5 ≥ 0.70`）、「真库尺度上闸门仍然咬人」（1000 篇档拒答率 `≥ 0.50`）与「装置量的是生产的行为」（`judgeQuery` 与 `recall()` 在 50 / 1000 两档上逐题判定一致）；原「装置真的会动」一条改成量「纯比例口径 vs 加地板」这一对，因为它的旧断言（生产值在 200 篇上拒答）**正是**被修掉的缺陷。（M5 又把其中两条用例的断言按新夹具重写，见 §5.5.2。）

### 5.5.2 M5 重建夹具（`bench/sweep-fixtures.mjs`）与「可满足性」的可证伪结论

M4 把「验收线无解」归因到夹具，M5 的活就是把那台夹具换掉、再回答一次同一问题。语料与题面生成整体抽到新文件 `bench/sweep-fixtures.mjs`（`sweep.mjs` 只留判分与扫描），旧夹具的两处不真实被逐条拆掉：

| 旧夹具（M3/M4 用的） | 新夹具（M5） | 怎么验的 |
|---|---|---|
| 判别词的 df **恒为 12**，与语料规模无关 | 服务名 df = 168（2000 篇档，占 8.4%）、知识点号 df = 覆盖服务数 2→4 | `test/sweep-fixtures.test.mjs` 量 df 随规模单调增长，并断言「不同取值 ≥ 4」显式否定恒为常数 |
| 可答题锚在**服务名**上 —— 而服务名在每一篇该服务的笔记里都有，所以「命中服务名」的文档覆盖率恒为 1.000 | 可答题锚在**（服务 × 知识点号）**上：`Lumenpath kp00000` 这篇是唯一同时含这两个锚的笔记 | 金标唯一性 + `verifyCorpus()` 断言：金标存在且唯一、正文含两个锚 |
| 不可答题 = 「服务名 + 一个通用词」（`Lumenpath 的命中率目标是多少？`），靠「问的那个词库里压根没有」制造难度 | 不可答题 = 「近邻同服务、同词表，但那个事实没写过」：`Lumenpath 的扩容台量 kp00022 是多少？` —— 服务在库、`kp00022` 在库、属性词在库，**只有这个组合不在库** | `verifyCorpus()` 逐条断言四个「在库」+ 一个「不在库」，且属性词的**切词结果**（不是整串）逐个查在库，杜绝生僻词 |
| 两类题覆盖率完全不可分（top-5 最大覆盖率 8 条不可答题全是 1.000，可答题最小的 12 条也全是 1.000） | 题面**同形**（同一个模板 `/^\S+ 的\S+ kp\d{5} 是多少？$/`），差别只在槽位 | 用例断言两类题题面形状只有 `answerable` / `refusal` 两种且同模板 |

**结果：验收线在新夹具上仍然无解，而且这次的归因是逐格可证伪的。** 生产口径（`PROD_PARAMS`）五档读数：`recall@5` **1.000 / 1.000 / 1.000 / 1.000 / 1.000**（旧夹具是 0.800 五档持平 —— 那个 0.800 的上界本身就是旧夹具的 `drop` 档人造出来的），拒答率 **0.000** 五档。把整个参数空间扫完 —— 5 档 × 7 个覆盖率 × 8 个 df 比 × 5 个 `minDocs` × 8 个地板 = **9835 格** —— `recall ≥ 0.80` 且拒答 `≥ 0.75` 的格子是 **0 个**；`recall ≥ 0.80` 的格子有 **9807** 个，其中拒答率**全部为 0.000**。拒答率 > 0 的格子一共只有 **28 个**，全部落在 50 篇档，而那 28 格的 `recall` **全是 0.000**（拒答率 ≥ 0.75 的 28 格同理）。也就是说：不是「最好的一组差一点」，而是**召回与拒答在这台装置上完全反相关，不存在折中点** —— 拒答只能靠把可答题一起拒掉来换。

为什么会这样，逐条给出机制（都能用 `judgeQuery(..., {minCoverage: null})` 逐题重放）：

1. **缺的不是「更严的阈值」，是一条机制。** 两道口径都在按设计工作：比例那一支确实把服务名判成非证据（2000 篇档 df=168、占 8.4% > 0.05）；而不可答题的判别词（知识点号 `kp00022`，df=2～4）是**孤例级的稀罕词，它自己就过了闸门**。所以「证据词筛得不够狠」说不通 —— 判别词在两类题里都是合格的证据词。
2. **覆盖率这一支结构上区分不了「金标」与「近邻命中了同一个判别词」。** `coveredIds()` 的分母是「证据词的 `idf × 权重`之和，每个词项**只算一次**」，分子是 `qWeight · tf(k1+1)/(tf + k1·norm)`，后者的上界是 ≈ 2.2 × 该词项的 idf。当判别词是孤例（df=2，idf≈4.6）而分母只剩它自己（≈ 4.6）时，**任何含它的文档覆盖率都被 `Math.min(1, …)` 顶到 1.000**。实测：2000 篇档的不可答题 top-1 是 `Cinderbay kp00022`（另一个服务的同一知识点），覆盖率 1.000，与金标 `Lumenpath kp00000` 的 1.000 逐位相同。
3. **所以「库里有近邻、事实不同」这件事，覆盖率闸门看不见**：它只能看见「这一篇有没有被问的判别词」，看不见「这一篇是不是被问的那**篇**」。要拒掉这类题，缺的机制是**组合级核对** —— 判定命中之后，再核一次「被问的服务 × 被问的知识点号是否在同一篇里共现」；共现则答，只有一边共现（即命中的是同一判别词的**别的服务**）则拒。这条机制现在不在 `src/core/` 里，M5 按铁律**没有动生产代码**，也没有用调常量的办法伪造一个拒答率出来。
4. **小语料档还叠了第二重失效**：`isInformativeTerm` 的第一支是 `df ≤ 64`，而 `df ≤ n`，所以 **n ≤ 64 时任何词项都算证据词**，闸门在 50 篇档等于没开。这一条与 M4 §5.5 第 4 点记的是同一个边界，只是这次它有了逐档读数。

**M5 交付的是「夹具不再说谎」，不是「验收线通过」**：旧夹具上那句「`recall ≥ 0.80` 且拒答 `≥ 0.75` 无解」可能是夹具的错；新夹具上同一句话是被 9835 格扫描 + 逐词项机制重放钉住的，并且指名了缺的那条机制（组合级共现核对）。回归用例 `test/sweep-fixtures.test.mjs`（6 条）把夹具契约与这条归因都变成断言，防止它被「调参调好了」的假象覆盖；`test/bench-sweep.test.mjs` 里两条依赖旧夹具结构的断言按新夹具重写（旧断言靠的是旧夹具的失真，不是真实行为）。判据 1 不受影响：`recall@5` 0.844 / `correct_refusal_rate` 0.80 / `injected_tokens_mean` 254.9 三项逐位不变（`bench/core-30-v1` 与 sweep 夹具互不相干）。

### 5.5.3 M6 补上「组合级共现核对」：五档各有一组参数同时满足召回与拒答

M5 把缺的机制指名到一行（§5.5.2 第 3 点：**判定命中之后再核一次「被问的实体 × 被问的知识点号是否在同一篇里共现」**）。M6 就是实现这一行，不调常量。新文件 `src/core/cooccurrence.js`（零依赖，与 `bm25.js` / `recall.js` 同层），接线点在 `src/core/bm25.js` 的 `scoreDocs()` 与 `src/core/recall.js` 的准入层。

**分离「这道闸开没开」与「这道闸这次有没有改变判定」**（沿用 §5.4 里 `informativeGateEnabled` 的既有语义，不新造），共现核对的四步：

| 步 | 做什么 | 代码 |
|---|---|---|
| 1 | 从查询里取**锚点**：只认 `source === 'term'`（同义扩展来的不算，那是猜的）且切词长度 ≥ 2 的词项，且 `df > 0`、`df/n ≤ COOC_ANCHOR_MAX_DF_RATIO = 0.5` | `anchorTermsOf()` |
| 2 | 按**词面形态**分成类：`digit`（`/[0-9]/`）、`han`（`\p{Script=Han}`）、`latin`（`\p{Letter}`）、`other` —— 「实体名 / 属性词 / 编号」在词面上天然是三类 | `termClass()`、`groupAnchorsByClass()` |
| 3 | **可核的类数按「库里认不认识这个词项」数**（`presentClasses()`：某一类里只要有一个词项 `df > 0` 就算），**不是**按「它够不够稀罕、能不能当锚点」数 | `requiredCooccurrences(known.length)` |
| 4 | 逐候选篇核：**每一类**都要在这一篇里命中（词面层，正文 + **笔记身份** `id`/`title`/`tags`/`aliases`）；缺任一类 → 这一篇不是答案 | `checkCooccurrence()` |

第 3 步是整个机制的要害，M6 前两版都栽在这里。绑定（哪些类能当核对点）是**对称**的，而被问的两半**不对称**：50 篇档 `Quartzwell 的温升步幅 kp00002 是多少？` 里 `quartzwell`（df=17/50=0.34）算锚点，但这座库里没有任何一篇把它和别的锚点类写在一起（`kp00002` 属于 Lumenpath/Tidalmark），于是它掉出绑定集。若按 `min(2, 绑定类数)` 数需求数，`lumenpath-kp00002` 只要「命中 han+digit 两类」就过 —— 而那篇一个字都没提 Quartzwell。**一个词项在库里存在就说明它可被问到，它没出现在候选篇里就是这一篇没写它**，这正是要拒答的情形。所以需求数按「库里存在的类数」算，「太常见」只影响稀有度读数、不再决定要不要核这一类。

## 机制怎么工作（判据 1 为什么不掉）

真库（`bench/core-30-v1`）的答案笔记**正文不复述实体名**：`project-kestrel-retry-count.md` 的正文是「同步失败后重试 5 次，间隔按指数退避…」，`Kestrel` 只出现在**文件名**里。只核正文时真库 `recall@5` 从 0.844 掉到 0.750（丢 c02/f03/k04 三条真答案）。修法是让**笔记身份**（`id` + `title` + `tags` + `aliases`）参与核对：`buildIndex()` 的 `metas` 多存一项 `identityTerms`（`identityTermsOf(doc)` 切词后**排序成数组**，不进 `postings`、不改 BM25 打分），`checkCooccurrence()` 把它并进候选篇的 present 集合。身份参与后真库 `recall@5 = 0.844`、`correct_refusal_rate = 0.8`、`answered_rate = 0.577`，与 M5 基线 `841b460` **逐位相同**（`node bench/run-eval.mjs --same-corpus --arms none,new`）。

## 小语料闸（`isInformativeTerm`）：现状与理由

任务 M6-2 要求「修小语料闸失效，且真库 1321 篇的既有断言原样通过」。**结论：没有可满足的修法，如实报告、不修。** 既有断言（`test/core-bm25.test.mjs:238-253`）要求 `isInformativeTerm(51, 51) === true` 且 `isInformativeTerm(5, 5) === true` —— 也就是 **`n ≤ 64` 时必须一律 true**；而「50 篇档闸门真的能咬人」要求 n=50 时存在**不**算证据的词项。这两条直接冲突：`df ≤ n` 恒成立，只要地板 ≥ n 就恒 true。改成纯比例（`df/n ≤ 0.05`）会让 `(51, 51)` 变 false，直接炸既有断言；改成「`n ≥ INFORMATIVE_MIN_DOCS = 200` 之前一律 true」则 50 篇档闸门仍然完全关闭，等于没修。两条路都不通，于是保留原式（`df <= Math.min(64, n) || df/n <= 0.05`），语义与改前**逐字等价**。

五档的达标不依赖这条闸：50 篇档的拒答全部由共现核对挣来（关掉它拒答率即 0.000）。这条闸在合成语料上的实际作用是**把服务名（50 篇档 df/n ≈ 0.34）排除出证据词**，与「50 篇档闸门关闭」并不矛盾 —— 纯比例那一支在大 n 上是有效的，小 n 上失效的只是绝对词频地板那一支。

**还没构造出来的对抗情形**：装置另有一档 `--traps`（把被取代的老笔记换成**没有取代标记**的坏副本，专门诱使旧值排第一）。默认语料上 `--traps` 也抓到 0（分母涨到 203、机会 70 次），说明当前题库还没构造出「有效性元数据正确、但旧值仍然被排到第一」的情形。也就是说：**这一期测到的是「取代关系没被写错」，不是「旧值即使没标错也抢不到第一名」**。后者要 M4 补：得构造「旧值与新值都有效、只有时间戳新旧不同」的题面，再看 `recencyOf` 的 30 天半衰期够不够。

**三条口径各自查什么**（出红时按这个顺序定位，不要一上来调算法）：

1. `recall@5` 低 → **先查索引**：`tabellio index --json` 的 `unreachable` 不为 0 就不是检索的问题（§3.1.1 的 `indexHidden` 就是这一类）。单跳事实题命中 <90% 即判定为索引问题。
2. `correct_refusal_rate` 低 → 查是**假命中**（不该命中的命中了）还是**阈值太松**。M2 的实测是前者：拒答题靠跨词碎片刷到 coverage ≥ 0.6（§5.4）。
3. `injected_tokens_mean` / `token_efficiency` 变差 → 查预算裁剪（`src/core/select.js`）有没有按 §5.2 的顺序丢，以及拒答是否照常返回（拒答不注入上下文）。

### 6.2 每题可追溯来源

一题一条记录。**当前题集的实际字段是 `id / kind / capability / prompt / expect[] / forbid[] / source[] / answer_aliases[] / expect_all / negative_transfer_probe`**（`bench/core-30-v1/tasks.json`；`capability`、`answer_aliases`、`expect_all`、`negative_transfer_probe` 已于 2026-10-17 落地）；`02-evaluation.md §4.6` 的 `gold_notes / expected{answer, judge} / setup.ops / difficulty / leak_check / tags` 仍是目标 schema，尚未落地（差异见 `02-evaluation.md §4.6.1`）。关键纪律：① **反向构题**——先选定一条记忆，再写一道只有它能回答的题，`source` 构造时即确定，不需要事后标注；② **防泄漏**——任务文本与 `source` 正文的字符 8-gram 重叠 >30% 退回重写，期望答案限长 ≤60 字，同答案命中多条 `source` 只算一次；③ **判分器优先级**——`substring/regex/归一化` > `set_match` > `refusal_match` > `cheap_judge`（配额 ≤20%）> 人工抽检（20%），拒答**必须用 refusal_match 判，不许让 LLM 裁判判「拒绝」**；④ **判分器本身要被评测**——用「含糊但切题」的对抗答案打自己的裁判（接受率目标 <20%，已落地 106 条对抗集），人工抽检记录 Cohen's κ（**未做**），κ<0.6 则该裁判分数不采信。

### 6.3 CI 怎么跑

| 频率 | 跑什么 | 门禁 |
|---|---|---|
| 每次 push | `core` 纯逻辑单测 + 一致性向量 + 索引重建幂等性（删掉 `index/` 重建，结果 hash 必须一致） | 必须绿 |
| 每次 push | 判据 1 的**子集**（单跳 6 题 + 拒答 4 题），纯集合判分，零模型成本 | 必须绿 |
| 每次 push | `tabellio index --json`：`unreachable == 0` 且 `stale == false`（索引健康是**可机检**的，不靠人记得去跑 `status`） | 必须绿 |
| nightly | 判据 1 全量 + 判据 2 成本曲线 + 判分器对抗测试 | 红则当日不许合入检索改动 |
| 每周 | 判据 3 时间回放的一个刻度（t0+2 周样本） | 红则冻结巩固功能 |

**索引重建的幂等性怎么验**（M2 落定，因为分层索引比平铺索引更容易踩到）：删掉 `index/` 重建，两次结果的 **hash 必须一致**。实现里有两个具体的不变量：

- **排序显式化**：叶组按 `(条数 desc, 组名 asc)` 排，不依赖 `Map` 的插入序 —— 只靠插入序会让「同名同条数的两个组」在两次重建之间对调，文件名里的序号跟着变，幂等性就成了随机通过。
- **生成的账要自洽**：写进索引的「列了多少条」必须等于实际指针行数。M2 在这里抓到一个真 bug：截断提示行 `- … 还有 N 条未列入索引` 自己以 `- ` 开头，被计数逻辑当成一条指针，于是 `indexHidden` 永远少 1；更要命的是当列出的条数恰好等于总数时，`truncated` 会算成 `false` —— 索引少了 1193 条而 `status` 报一切正常。**一个 off-by-one 能让整套账说谎**，所以 `countPointerLines` 必须排除提示行，且这条要有单测钉住。

评测成本上限来自 `00-brief.md §5` 判据 B：一次完整评测本地一条命令跑完、≤15 分钟、≤$2；单轮评测总量级 ≈10^5 tokens（`02-evaluation.md §4.4`）。`--system ledger_replay` 与 `--system none` 两条对照线用来验证评测脚手架本身没坏。

**代价**：把「注入 token」当一等指标意味着检索质量提升如果靠多注入换来的，一律不算数——这会让 M1/M2 的进度看起来比实际慢。**什么时候该换**：如果连续两个里程碑都卡在判据 2 且用户真实反馈是「答不出来」，说明我们的成本闸门比用户的耐心还紧，该把默认预算从 500 抬到 1000 并重测拐点，而不是继续优化算法。

## 7. 与旧系统的关系

- **旧库是数据源**：`~/memory/engramory` 的 72 篇 / 646 KB 直接作为导入样本与真实语料（`00-brief.md §8`）。导入器 `packages/import-engramory/` 负责把旧 frontmatter 映射到 `memory.note/1`，冲突字段进人工队列，不猜。
- **旧库是基线**：`--system ledger_replay` 把旧账本回放成检索侧基线；判据 1 的对照三档是 `none`（无记忆）/ `engramory`（旧插件）/ `new`（本服务）（`02-evaluation.md §4.7`）。
- **赢了才算数**：判据 A 要求新服务显著优于旧插件与无记忆（`00-brief.md §5`）。**赢的是长板，不是把旧插件判死**（`00-brief.md §10`）。**第一条线不冻结**（作者 2026-10-16 定调）。
- **共享内核**：`00-brief.md §10` 定了「存储、检索、账本、评测口径抽成 `memory-core`，两个壳都依赖它」。本文的 `packages/core` 就是这个包；旧插件接入方式为「依赖发布版 `@yffto/memory-core`」，共享内核的破坏性变更要同时跑两边测试，发布互不阻塞。
- **不共享运行时数据**：旧插件继续用 `~/memory/engramory/`；新服务用自己的 `data/`（默认 `~/memory/<product>/`）。

**代价**：两边共享内核意味着 `core` 的 API 变更要过两套测试、两套发布节奏，任何激进重构都会变慢；不共享数据意味着「在 DSH 里聊定的东西在 Claude Code 里看不见」，跨宿主连续这个卖点要等本服务自己用起来才成立。**什么时候该换**：如果到 M4 旧插件的用户数仍远大于新服务，说明「通用化」的用户价值低于「深挖单宿主」——那时该把 `core` 冻结成只读兼容层，把预算全投回第一条线，而不是继续两头维护。

## 9. 关键接口草案

五个操作，收敛到 5±2 个（`03-hosts-and-interfaces.md` 的结论）。默认只读；写操作带行为提示（`read-only` / `idempotent` / `destructive`，照抄 Basic Memory 的渐进式工具发现做法）。下面保留关键字段与全部返回形态（成功 / 幂等 / 拒绝 / 跳过 / 错误），实现者按此签名建类型。

> **现状**：`remember` / `recall` / `explain` / `verify` / `consolidate`（`invalidate` / `archive`）/ `undo` 已实现（CLI；MCP 工具面为 recall/search/read/list/status，加 `--allow-write` 后多 `remember` 与 `capture`，后者只写候选）。`recall` 在 MCP 侧是只读的预算感知读接口：文本结果给正文，`structuredContent` 只给元数据（不重复正文），拒答不是错误。`explain` / `verify` 目前只服务 **recall 回执**：`explain` 接受 `--query` 或 `--receipt`，`verify` 只接受 `--receipt`，不接受 `id` / `turn_id`，也不返回 `ledger_events`。`consolidate --merge/--summarize/--promote` 只有**提案层**：出草稿、不落盘、`--apply` 退 2。`forget`、写入回执、replay、内容类执行层尚未实现；下面的 JSON 是目标接口，`consolidate` 的实际返回以其后标注为准。

```js
// ── remember：写入。热路径，零 LLM 调用。幂等（同 scope 同内容返回已有 id）
remember({
  content,                      // string，≤400 字；超长由调用方切分（04-cost-model.md 第 13 条）
  kind,                         // core | semantic | episodic | procedural
  scope,                        // user | project:<git origin 指纹>；默认由宿主注入
  trust,                        // user_stated | system_derived | external
  provenance: { written_by, source_ref, derived_from? },
  valid_from?, valid_to?,
  subject?, predicate?          // 有这两个字段才参与自动冲突消解
})
// → 成功
{ ok: true, id, status: "stored", superseded: [id...] }   // superseded 只在提供了 subject/predicate 时非空
// → 幂等 / 拒绝 / 跳过（都是正常返回，不是异常）
{ ok: false, status: "duplicate", existing_id }
{ ok: false, status: "skipped",   reason: "chitchat" | "too_short" | "no_durable_content" }
{ ok: false, status: "denied",    reason: "scope_forbidden" | "trust_violation"
                                            | "would_promote_external_to_instruction" }
// → 错误（真异常：IO / schema / 库不可写）
{ error: { code: "E_STORE_READONLY" | "E_SCHEMA_UNSUPPORTED" | "E_LOCK_TIMEOUT", message, retryable } }

// ── recall：读取。默认操作，永远只读。
recall({
  query,
  scope?,                       // 省略 = user + 当前 project
  budget_tokens = 500,          // 硬预算；服务端裁剪并报告裁掉了什么
  kinds?, as_of?, since?,       // as_of：按 valid_from/valid_to 取「当时为真」的快照
  explain = false               // true 时返回 why_these，用于面板与调试
})
// → 有证据（items 里每条都带来源、有效期与打分拆解，why 即「为什么给了它」）
{ ok: true, status: "ok", items: [
    { id, content, kind, trust, confidence, valid_from, valid_to, supersedes, superseded_by,
      source: { written_by, source_ref },
      score: { importance, recency, relevance, total },
      why: "core 档：身份/硬偏好" | "词法命中 3.2" | "被 2 条 episodic 支撑" } ],
  budget: { requested: 500, used: 412, dropped: [{ id, reason: "episodic_low_trust" }] } }
// → 证据不足（一等公民，不是错误）
{ ok: true, status: "insufficient_evidence",
  why_not: "top_score_below_threshold" | "only_external_low_trust"
          | "all_hits_expired" | "conflicting_values_no_time_order"
          | "cooccurrence_required_pair_missing",  // M6 §5.5.3
  nearest: [ { id, score } ] }   // 供调用方决定要不要放宽
// → 拒绝
{ ok: false, status: "denied", reason: "scope_forbidden" | "budget_below_minimum" }

// ── consolidate：整理。显式、可选。绝不在热路径被调用。
// 当前实现两种只动元数据的操作（另有内容类提案层，见本段末尾）：
// invalidate：B.supersedes 含 A，且 A active、无 valid_to、无 superseded_by
//   → 写 A.valid_to=now + A.superseded_by=B；正文一字不改，as_of 仍可查。
// archive：显式 archiveIds 点名，且 A active、无 valid_to、无 superseded_by、now 有效
//   → 只写 A.status=archived；不写 valid_to/superseded_by；默认检索面（含 as_of）排除。
consolidate({
  scope?, kinds?,               // 过滤扫描面
  archive?: [id...],            // 只归档这些 id；可逗号分隔，去重
  apply = false,                // CLI 默认 dry-run；API 用 apply:true 才写
  max_change_ratio = 0.05       // allowed = max(1, floor(scanned × ratio))，两种操作共用
})
// → 计划（dry-run：不落盘、不改库）
{ ok: true, status: "planned", run_id, dry_run: true,
  operations: [{ op: "invalidate" | "archive", id, superseded_by, valid_to, rationale,
                 before: { status, valid_to, superseded_by, body_sha256 },
                 after:  { status, valid_to, superseded_by, body_sha256 },
                 est_tokens: 0 }],
  skipped: [{ id, reason }],
  stats: { scanned, planned, invalidate, archive, allowed, change_ratio, est_tokens } }
// → 已执行（写 runs/<run>.plan.json + runs/<run>.json）
{ ok: true, status: "applied", run_id, plan_path, receipt_path,
  applied: n, skipped: n, reversible: true, operations, receipt,
  stats: { scanned, planned, invalidate, archive, allowed, change_ratio, est_tokens,
           applied, skipped, failed } }
// → 主动中止（保险丝 / 回执写失败；receipt 失败会回滚已改字段）
{ ok: false, status: "aborted",
  reason: "change_ratio_exceeded" | "plan_write_failed" | "receipt_write_failed" }
// → 撤销（CLI: consolidate --undo <run>；先全量预检，冲突整单拒绝）
{ ok: true, status: "undone" | "already_undone", run_id, receipt_path, undo_path,
  restored: n, skipped: n }
{ ok: false, status: "conflict" | "tampered" | "partial" | "unreadable", ... }
// ── 内容类提案（CLI: consolidate --merge/--summarize/--promote --json）
// 只读扫描 + 纯草稿；不写 runs/、notes/、notes/candidates/，因此没有 receipt / undo。
// 目标路径：merge/summarize → notes/<新 id>.md；promote → notes/candidates/<新 id>.md。
{ ok: true, status: "proposed", proposal_id: "prop_...",
  mode: "merge" | "summarize" | "promote",
  dry_run: true, apply_supported: false, would_write: false,
  source_ids: [id...], sources: [ { id, title, chars, tokens, body_sha256 } ],
  target: { id, path, status: "draft", scope, kind, trust,
            draft_kind: "deduped_concat" | "extractive" | "scaffold",
            requires_review: true, supersedes: [id...], body, chars, tokens },
  warnings: [ { code, message } ],
  stats: { scanned, sources, source_chars, source_tokens, target_chars, target_tokens,
           saved_chars, saved_tokens, saved_ratio, estimated_write_ops,
           estimated_change_ratio, distinct_days },
  next_action: "人工审阅提案；执行层未实现，当前不会写任何文件。" }
{ ok: false, status: "rejected", reason: "invalid_mode" | "missing_sources" | "source_invalid"
  | "scope_mismatch" | "kind_mismatch" | "source_too_short" | "not_enough_time_points"
  | "target_id_exists" | ..., dry_run: true, apply_supported: false, would_write: false, ... }
// 目标但未实现：内容类执行层、replay、diff.jsonl、budget_tokens

// ── forget：遗忘。两级，默认软。
forget({ id?, query?, scope?,
         mode = "archive" })    // archive（软，可恢复） | expire（设 valid_to=now） | purge（真删，需二次确认）
// → { ok: true, status: "archived" | "expired" | "purged", ids: [...], recoverable_until? }
// → { ok: false, status: "denied", reason: "purge_requires_confirmation" | "core_kind_protected" }

// ── explain：可观测性。回答「为什么给了它 / 为什么没给」。
explain({ query?, id?, turn_id? })
// → { ok: true, answer: {
//      recalled: [ { id, score_breakdown, why } ],
//      not_recalled: [ { id, why_not: "below_threshold" | "scope_mismatch"
//                                | "expired_at_as_of" | "budget_dropped" | "never_indexed" } ],
//      ledger_events: [ { ts, kind, ... } ] } }
```

**为什么这样切**：① **`remember` 与 `consolidate` 彻底分开**——热路径不许改旧记录，合成一个 API 会让「整理」重新爬回热路径（旧项目的病）；② **`insufficient_evidence` 是 `ok: true`，`deny` 也是正常返回**——拒答是正常结果不是错误，写成 `error` 会诱导调用方重试或编造，而写入闸门被绕过的主要原因就是它报异常、调用方 catch 之后照样往下走；③ **`consolidate` 默认 `dry_run: true`**——默认不动数据，要动必须显式 `apply`；④ **`recall` 返回 `why` 与 `budget.dropped`，所有写操作带 `scope`**——`00-brief.md §6` 原则 8（一切可观测）的落地形态，作用域是隔离的基本单位而不是可选项。

**代价**：五个原语意味着模型侧记忆工具（Anthropic `memory_20250818` 的 view/create/str_replace/insert/delete/rename）无法直接映射，将来若要对接得写一层适配；`budget_tokens` 这种「调用方管预算」的设计把压力转移给宿主，宿主实现得不好时我们会看起来很贵。**什么时候该换**：若 MCP 规范出现官方记忆原语（赌注 B 不成立，见 `05-agi-direction.md §6`），写一个 adapter 即可迁移——因为它是「工具 + 记录」形状，不是专有协议。

## 10. 风险与代价

每条都是「为什么选它 / 代价是什么 / 什么时候该换」。

**1. 真相源 = 纯文本文件（而不是数据库）**
选它：可 `cat`、可 git、可带走、跨宿主零同步；被 Anthropic 客户端 memory tool 与 `AGENTS.md` 约定两条独立线索验证（`05-agi-direction.md` 赌注 A）。
代价：万级记录后扫描与索引重建变慢；手改文件会破坏解析（对策：fail-closed + `doctor` 暴露失败数）；无法做原子跨文件事务。
该换：记录数进万级且增量索引仍超预算，或出现必须跨文件原子性的场景（如带配额的团队共享）——那时引入数据库，但**它只能是索引不是真相源**。

**2. 默认零 API 成本（纯词法 + 可选本地向量）**
选它：插件市场用户必须「装上就跑」，`onnxruntime-node` 解包 301 MB、`@huggingface/transformers` 实际 ≈310 MB+，作为默认依赖不可接受（`04-cost-model.md`）；默认档成本 ¥0。
代价：召回质量比云端低约 6pt（hit@1 68.4% vs 74.7%）；要开向量得让用户先跑一个本地端点（Ollama / llama.cpp server）。
该换：若判据 1 在纯词法档不达标而本地向量达标（见 §5.3）。

**3. 默认 pull，push 只留 ≤400 字核心档**
选它：全行业事实标准是 pull；旧项目 push 的打开率只有 2.4%（`00-brief.md §2`）。省钱清单里「pull 而非 push」标为必须做（`04-cost-model.md`）。
代价：模型不主动问就拿不到记忆 → 短期体验上「记忆能力变弱」；核心档那 400 字永远占上下文。
该换：若真实使用中宿主 agent 的 `recall` 调用率长期过低（说明宿主侧集成没做好），该改的是工具描述与系统提示，而不是回到 push。

**4. 热路径零 LLM，整理全放空闲期**
选它：sleep-time compute 有可复现数字（同等准确率测试时算力 ↓~5×；加大 sleep-time 算力准确率 +13%/+18%，`05-agi-direction.md §3.5`）。
代价：巩固滞后 → 刚写完的重复/冲突事实有一段时间共存；`consolidate` 必须显式触发或常驻，多一个进程要保活。
该换：若查询可预测性高的场景下（论文明确说查询越可预测收益越大）注入质量明显输给对手，可提高巩固频率，但**不把整理搬回热路径**——那是旧项目已经证伪过的形态。

**5. 写入带信任等级 + 记忆内容不得成为指令**
选它：提示注入通过记忆传播是已知攻击链（不可信内容被读 → 被写入 → 后续被当既定事实注入），硬约束是「记忆内容永远不能提升为指令」（`05-agi-direction.md §5.3`），且这可静态检查。
代价：外部来源的记忆基本只能进 `semantic`，不能进 `procedural`，能力上限被压低；每条都要带 provenance，写入路径更长。
该换：永不放松。若某天要支持「外部文档自动成为规则」，那必须是显式人工确认的流程，不是默认行为。

**6. MCP 单一接口 + 常驻核心 + stdio 薄壳**
选它：stdio 是 11 个宿主全部支持的公共子集；常驻核心做唯一写者，避免多宿主并发写坏库（`03-hosts-and-interfaces.md`）。Dual-era（同时兼容 2026-07-28 与 2025-11-25）是必须的，因为两个方向都会直接失败。
代价：两套入口各自要测；核心不在时的行为必须显式设计（退化为只读）；本地 HTTP 是攻击面（只绑 127.0.0.1、token 文件 0600、禁止进日志）；老客户端兼容矩阵要长期维护。
该换：若沙箱/容器环境里 HTTP 长期不通（`03-hosts-and-interfaces.md` 已提示这个风险），退化到「纯 stdio，每宿主一个进程 + 跨进程文件锁」，代价是写并发与索引重复构建变常态成本。

**7. 索引必须是可重建的派生物**
选它：真相源唯一化之后，索引正确性问题全部变成「重建一次」的问题；`index = f(notes)` 让 CI 可以断言「重建结果 hash 一致」。
代价：增量索引逻辑与重建逻辑必须严格等价，否则会出现「日常用增量、重建后才暴露」的漂移（对策：CI 每次 push 跑幂等性测试）；向量索引绑定模型指纹，换模型 = 全量重建。
该换：不做。这条是审计性的地基。

**8. 成本闸门默认 `degrade` 而不是 `block`**
选它：超预算时退回纯词法仍可用；阻塞会让服务在预算用尽后彻底不可用（`04-cost-model.md`）。
代价：用户可能长期在降级状态下使用而毫无察觉，质量悄悄变差。
该换：如果 `explain` 显示降级状态持续 >7 天，说明预算定得太低——该调预算，而不是把 `degrade` 改成 `block`。

**9. 评测先行（先写 schema 与基线，再写检索代码）**
选它：整个领域没有一个可以直接采信的公开数字（`02-evaluation.md`）；旧项目的真正尸检报告是 `hit_but_unused_rate`——「命中」「注入」「使用」必须拆成三个独立事件。
代价：M0/M1 的产出看起来「没有功能」；判据严苛会让进度显得慢。
该换：不做。没有这条，判据 A 会在两周内变成摆设（`00-brief.md §5` 判据 B 的原话）。

**10. 最值得下注的一条（同时是最大风险）**
选它：赌「记忆的形态固定在文件/记录约定 + 能读它的工具」而不是独立 SaaS（`05-agi-direction.md` 赌注 A，最硬的证据是 Anthropic 把 memory tool 放在客户端、记忆存在用户自己的应用里）。
代价：如果三年内模型原生记忆吃掉个人助手场景，文件层会显得冗余，用户价值被吃掉大半。
该换：坚持纯文本可导出——这条不成立时用户至少能迁移，我们随时能变成「导出 + 审计 + 跨宿主搬运」的补充工具；**反之若一开始把数据锁进私有存储，这条不成立时会死透**。
